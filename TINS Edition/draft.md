# Draft Questions for TINS Specification

## Project Title and Description
1.  What is the name of the software?
    *   Gemini Fullstack LangGraph Quickstart
2.  What is its overall goal and purpose?
    *   This project demonstrates a fullstack application using a React frontend and a LangGraph-powered backend agent. The agent is designed to perform comprehensive research on a user's query by dynamically generating search terms, querying the web using Google Search, reflecting on the results to identify knowledge gaps, and iteratively refining its search until it can provide a well-supported answer with citations. This application serves as an example of building research-augmented conversational AI using LangGraph and Google's Gemini models.

## Core Logic and Features (for `model.py` specification)
3.  What are the main functions, computations, processes, or behaviors the application needs? Describe them step-by-step or in terms of inputs/outputs.
    *   The backend agent performs the following steps:
        1.  **Generate Initial Queries:** Based on user input, it generates a set of initial search queries using a Gemini model.
        2.  **Web Research:** For each query, it uses the Gemini model with the Google Search API to find relevant web pages.
        3.  **Reflection & Knowledge Gap Analysis:** The agent analyzes the search results to determine if the information is sufficient or if there are knowledge gaps. It uses a Gemini model for this reflection process.
        4.  **Iterative Refinement:** If gaps are found or the information is insufficient, it generates follow-up queries and repeats the web research and reflection steps (up to a configured maximum number of loops).
        5.  **Finalize Answer:** Once the research is deemed sufficient, the agent synthesizes the gathered information into a coherent answer, including citations from the web sources, using a Gemini model.
    *   (Note: This backend logic corresponds to the `model.py` role mentioned in `scuffedepoch-sysp.md`, primarily implemented in `backend/src/agent/graph.py` and its supporting files like `state.py` and `prompts.py`.)

## Data Structure and Handling (for `model.py` specification)
4.  What kind of data does the application use?
    *   User input (text queries).
    *   Search queries (text, generated by an LLM based on user input).
    *   Content from project files (text, acting as substitutes for web research results in the modified graph).
    *   Source information (file paths, type of source).
    *   Internal agent state data (e.g., sufficiency flags, knowledge gaps identified, loop counts).
    *   Configuration parameters (e.g., model names, number of queries, maximum research loops).
    *   Final synthesized answers (text, generated by an LLM with citations).
    *   Chat history (list of messages exchanged between user and agent).
5.  How is it stored, retrieved, processed, or managed?
    *   Data is primarily managed within typed dictionaries defined in `backend/src/agent/state.py` (e.g., `OverallState`, `ReflectionState`, `QueryGenerationState`, `WebSearchState`).
    *   This state is passed between different nodes of a LangGraph graph defined in `backend/src/agent/graph.py`.
    *   User messages and AI responses are accumulated in the `messages` field of `OverallState`.
    *   Generated search queries (which are file paths in this modified version) are stored in `query_list` (in `QueryGenerationState`) and then processed individually.
    *   Content retrieved from files (simulating web research) is stored in `web_research_result` and metadata about these sources (like file path) in `sources_gathered` within `OverallState`.
    *   The `reflection` node processes `web_research_result` to determine if information is sufficient and if follow-up queries (more file reads) are needed.
    *   The `finalize_answer` node synthesizes the information from `web_research_result` and `sources_gathered` into a final answer.
    *   The `OverallState` object holds the comprehensive state throughout the agent's execution flow. LangGraph itself handles the persistence and checkpointing if configured (though the provided files focus on the in-memory state flow).
6.  Define key data entities and their properties/relationships conceptually (e.g., using JSON-like structure).
    *   The key data structures are defined as TypedDicts in `backend/src/agent/state.py`:
        ```python
        class OverallState(TypedDict):
            messages: Annotated[list, add_messages] # History of user and AI messages
            search_query: Annotated[list, operator.add] # List of search queries (file paths) made
            web_research_result: Annotated[list, operator.add] # List of contents read from files
            sources_gathered: Annotated[list, operator.add] # List of dictionaries detailing sources (e.g., {'type': 'file', 'source': 'path/to/file', 'content': '...', 'id': 0})
            initial_search_query_count: int # Number of initial queries to generate
            max_research_loops: int # Maximum iterations for the research loop
            research_loop_count: int # Current iteration count of the research loop
            reasoning_model: str # Name of the LLM model to use for reasoning

        class ReflectionState(TypedDict):
            is_sufficient: bool # Flag indicating if gathered information is sufficient
            knowledge_gap: str # Description of any identified knowledge gap
            follow_up_queries: Annotated[list, operator.add] # List of new queries (file paths) to explore
            research_loop_count: int # Current iteration count
            number_of_ran_queries: int # Total queries executed so far

        class Query(TypedDict): # Represents a single search query (file path in this context)
            query: str # The file path
            rationale: str # Justification for this query (less relevant for file paths)

        class QueryGenerationState(TypedDict):
            query_list: list[Query] # List of Query objects to be processed

        class WebSearchState(TypedDict): # State for the (file reading) node
            search_query: str # The file path to read
            id: str # An identifier for this specific read operation
        ```
    *   The `OverallState` is the central data structure that evolves as the agent graph progresses. Other states represent data at specific stages of the agent's process.

## User Interaction and Event Handling (Connecting `main.py` to `model.py`)
10. How does the user interact with the UI (in `main.py`)?
    *   This is a React/TypeScript frontend, not Python/`main.py`. User interactions include:
        *   Typing text into the `Textarea` for queries.
        *   Clicking buttons: "Search", "Stop", "New Search", "Copy".
        *   Selecting values from the "Effort" and "Model" `Select` dropdowns.
        *   Pressing the Enter key in the `Textarea` (when not holding Shift) to submit the form.
        *   Expanding/collapsing the "Research" `ActivityTimeline`.
11. What actions (button clicks, text input) should trigger specific logic in the `model.py`?
    *   Again, referring to the React frontend and LangGraph backend:
    *   Submitting the `InputForm` (either by clicking the "Search" button or pressing Enter in the `Textarea`) triggers the `handleSubmit` function in `App.tsx`.
    *   This function then calls `thread.submit()` with a payload containing:
        *   The current list of messages (including the new human input).
        *   `initial_search_query_count`: Derived from the "Effort" selection (e.g., Low=1, Medium=3, High=5).
        *   `max_research_loops`: Derived from the "Effort" selection (e.g., Low=1, Medium=3, High=10).
        *   `reasoning_model`: The string value from the "Model" selection (e.g., "gemini-2.0-flash-preview-04-17").
    *   This `thread.submit()` sends the data to the LangGraph backend agent, initiating its research process.
12. How should the `model.py` signal updates back to the UI (`main.py`)?
    *   The frontend uses the `useStream` hook from `@langchain/langgraph-sdk/react` to establish a streaming connection with the backend agent.
    *   The backend (LangGraph agent) streams events and data back to the frontend.
    *   The `useStream` hook has an `onUpdateEvent` callback. When the backend sends an event (e.g., `generate_query`, `web_research`, `reflection`, `finalize_answer`), this callback is triggered in `App.tsx`.
    *   Inside `onUpdateEvent`, the event data is processed to create a `ProcessedEvent` object, which is then added to the `processedEventsTimeline` state. This state is used to render the live `ActivityTimeline`.
    *   The `messagesKey: "messages"` configuration in `useStream` tells the hook to update the `thread.messages` state whenever the backend stream includes a new list of messages. This automatically re-renders the `ChatMessagesView` to display new human or AI messages.
    *   The `thread.isLoading` state variable, managed by `useStream`, reflects whether the backend is currently processing, allowing the UI to show loading indicators or change button states.
    *   When the final AI message is received and `thread.isLoading` becomes false, the `processedEventsTimeline` for that interaction is stored in `historicalActivities` associated with that AI message's ID.

## Error Handling and Validation
18. What potential errors (invalid input, failed API calls, file errors) should the application anticipate?
    *   **Backend (`graph.py` / LLM Interaction):**
        *   `GEMINI_API_KEY` not configured: The application will fail on startup.
        *   LLM API errors: Failures in calls to Google Gemini (e.g., quota exceeded, network issues, invalid requests). `ChatGoogleGenerativeAI` is set with `max_retries=2`.
        *   Errors from the Google Search API if it were being used directly (though it's used via Gemini model in the original design).
    *   **Backend (File Handling in modified `web_research` node):**
        *   `FileNotFoundError`: If a file path provided as a "search query" does not exist.
        *   General `Exception`: Other issues during file reading (e.g., permissions).
        *   Invalid query type: If the "search query" (expected file path) is not a string.
    *   **Frontend (`App.tsx`):**
        *   User submitting an empty query (currently handled by disabling the submit button).
    *   **General/Deployment:**
        *   Network connectivity issues between frontend and backend.
        *   If fully deployed as per README suggestions: issues with Redis or Postgres.
        *   Docker build failures if frontend build fails or Python dependencies cannot be installed.
        *   Frontend not found: `app.py` serves a 503 if the frontend build directory is missing.
19. How should these errors be handled in both the `model.py` logic?
    *   **`GEMINI_API_KEY` not set:** Raises a `ValueError` in `graph.py` during module initialization, preventing the agent graph from being built and the application from starting correctly if the key is essential at that stage.
    *   **LLM API errors:** The `ChatGoogleGenerativeAI` instances are configured with `max_retries=2`. If retries are exhausted, the LangChain library typically raises an exception. Within LangGraph, an unhandled exception in a node would likely cause the current agent run for that thread to error out. The stream to the client might terminate or send an error event (behavior depends on LangGraph's SDK error propagation).
    *   **File Handling errors in `read_project_file` (within `web_research` node of `graph.py`):**
        *   `FileNotFoundError` or other `Exception`: The function catches these exceptions. An error message string is created. This message is then included in the `content` field of an item in the `sources_gathered` list (with an `error: True` flag) and also as an item in the `web_research_result` list.
        *   `Invalid file path type` in `web_research` node: An error message is returned in `sources_gathered` and `web_research_result`.
        *   These error messages effectively become part of the "researched data" and are passed to subsequent nodes (like `reflection` and `finalize_answer`). The final AI-generated answer might then include information about these file reading errors if the `finalize_answer` prompt and LLM decide to surface them.
    *   **General LangGraph errors:** LangGraph has its own error handling for graph execution, but specific application-level responses to these (beyond what the SDK provides to the frontend) are not detailed.
20. How should errors be presented in the `main.py` UI?
    *   The React frontend code reviewed (`App.tsx`, `ChatMessagesView.tsx`) does not have explicit, distinct UI components or modals for displaying errors that might originate from the backend agent's operations (e.g., API call failures during research, LLM errors).
    *   The `onFinish` callback in `useStream` in `App.tsx` does `console.log(event)`, which could include error information if the stream finishes due to an error, but this is not shown to the user in the UI.
    *   If the backend agent sends an error message as part of the regular AI message content (e.g., within `message.content`), then it would be rendered in the `ChatMessagesView` via `ReactMarkdown`.
    *   The `web_research` node in `backend/src/agent/graph.py` was modified to read files and includes `try-except` blocks. If a file is not found or another error occurs during reading, it returns an error message within the `content` of `sources_gathered`. If this content is then used by the `finalize_answer` node to form the AI's response, that error message would appear in the chat.
    *   There is no specific global error banner or pop-up displayed for backend issues. Frontend input validation is minimal (e.g., submit button disabled if input textarea is empty).
